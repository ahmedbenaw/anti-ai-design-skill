### M23 — swiftui-pro/references/design.md, accessibility.md, hygiene.md
- **Source:** Paul Hudson, repo reference files, retrieved 2026-09-05. https://raw.githubusercontent.com/twostraws/SwiftUI-Agent-Skill/main/swiftui-pro/references/design.md
- **Context:**
  - design.md: "Avoid hard-coded values for padding and stack spacing unless specifically requested"; prefer a shared enum of design constants; avoid fixed frames; enforce Apple's 44×44 minimum tap target strictly.
  - design.md also: "Use `bold()` instead of `fontWeight(.bold)`" and warns against "scattering around `fontWeight(.medium)` or `fontWeight(.semibold)`" — a specific, regex-able habit.

  - design.md notes `ContentUnavailableView` and `Label` exist and should be preferred over hand-rolled empty states and icon+text `HStack`s — AI output that hand-rolls both is doing more work than the platform requires.
- **Tags:** `[AVOID: hardcoded font sizes / padding / fixed frames in SwiftUI]` `[EVIDENCE-ONLY]`
- **Feeds:** MOB4, MOB5

### M24 — swiftui-pro/references/views.md
- **Source:** Paul Hudson, repo reference file, retrieved 2026-09-05. https://raw.githubusercontent.com/twostraws/SwiftUI-Agent-Skill/main/swiftui-pro/references/views.md
- **Context:**
  - The single most-repeated rule in the file (stated twice deliberately): "Strongly prefer to avoid breaking up view bodies using computed properties or methods that return `some View`... Extract them into separate `View` structs instead, placing each into its own file."

## Candidate tells

For every candidate the false-positive note is structured around three populations: **expert human**, **beginner human**, and **tool scaffold**. A tell that only separates AI from experts is worthless — it will fire on every junior developer's app.

---

### MOB1 — Untouched Jetpack Compose default purple palette
**Description:** The shipped app still contains the Android Studio Empty Activity default theme values `Purple80/PurpleGrey80/Pink80/Purple40/PurpleGrey40/Pink40` with their original hex values.
**Support:** M25 (direct measurement of the artifact, byte-identical across two unrelated repos).
**Regex:** yes.
```
0xFFD0BCFF|0xFFCCC2DC|0xFFEFB8C8|0xFF6650a4|0xFF625b71|0xFF7D5260
```
(Case-insensitive on the hex digits. Match the **values**, not the names — M25 shows the names survive customization while the values change, so name-matching would fire on customized themes.)
**Era:** 2021→present (Material 3 Compose templates). Stable; low stale-risk.
**False positives:** Expert human — rare, they replace the theme. Beginner human — **very high**, this is the literal untouched scaffold. Tool scaffold — this *is* the scaffold. **Verdict: PASSES the evidence bar but only as a weak "nobody customized this" signal, never as AI attribution.** It is evidence of an unstyled project, which correlates with generated code but is equally consistent with a human's first Android app or a fresh prototype. Must never be scored above the lowest severity band, and must never fire alone.

### MOB2 — Untouched Expo scaffold artifacts
**Description:** Shipped React Native code still carries `create-expo-app`'s literal placeholders. Two distinct fingerprints, because two templates are in play:
- **tabs template** (`--template tabs`): tab titles `'Tab One'`/`'Tab Two'`, tint `#2f95dc`, `tabIconDefault: '#ccc'`, and the same `chevron.left.forwardslash.chevron.right` / `code` icon on *every* tab.
- **default template** (bare `create-expo-app`): the `Home`/`Explore` tab pair with route files `index.tsx` + `explore.tsx`, the accent-free palette literals `#F0F0F3` / `#E0E1E6` / `#60646C`, and the `expo-router/unstable-native-tabs` import.

**Support:** M26 and M36 (two primary artifacts, official Expo scaffold source).
**Regex:** yes.
```
['"]Tab (One|Two)['"]|#2f95dc|tabIconDefault:\s*['"]#ccc['"]|chevron\.left\.forwardslash\.chevron\.right|expo-router/unstable-native-tabs|#F0F0F3|#E0E1E6
```
Precision differs sharply across these alternatives: `"Tab One"` and `#2f95dc` are near-conclusive abandonment markers; `Home`/`Explore` and the neutral greys are weak, because those are also perfectly reasonable choices a developer would arrive at independently. Score them separately rather than as one regex hit — treat the `unstable-native-tabs` import and grey literals as corroborating context only.
**Era:** Expo Router era, ~2023→present. **High stale-risk** — the default template changed shape between the two versions examined here (M26 uses `Tabs`, M36 uses `NativeTabs`). Re-verify all literals against `expo/expo` before each release of the skill.
**False positives:** Expert human — near zero for `"Tab One"`; moderate for the `Home`/`Explore` half. Beginner human — high. Tool scaffold — this *is* the scaffold. **Verdict: PASSES, on the tabs-template literals.** `"Tab One"` is the single highest-precision item in this whole sweep for "this screen was never designed", though it identifies *unfinished*, not *AI-authored*. Same-icon-on-every-tab is the visually loudest consequence and is worth surfacing in the human-readable report. The default-template half passes only as corroboration.

### MOB3 — Deprecated SwiftUI API cluster (training-cutoff staleness)
**Description:** A project targeting recent iOS that nevertheless uses the pre-iOS-17 SwiftUI vocabulary: `.foregroundColor(`, `.cornerRadius(`, `.tabItem`, `NavigationView`, `PreviewProvider`, `.navigationBarLeading`/`.navigationBarTrailing`, `Text(...) + Text(...)` concatenation, `overlay(_:alignment:)`.
**Support:** M21/M22 — **one source only** (Paul Hudson's rule-set). M23/M24 are the same author and do not corroborate independently. M21 supplies the mechanism explicitly ("they frequently use deprecated API"), but no measurement exists.
**Regex:** yes.
```
\.foregroundColor\(|\.cornerRadius\(|\.tabItem\b|\bNavigationView\b|\bPreviewProvider\b|\.navigationBarLeading\b|\.navigationBarTrailing\b
```
**Era:** the boundary is iOS 16→17 (2023) for most of these; it moves every year, so this is inherently `[STALE-RISK]` and the pattern list must be dated.
**False positives:** Expert human — **very high in any pre-2023 codebase.** A well-maintained six-year-old app is legitimately full of `.foregroundColor`; deprecation is not removal and Apple keeps these working. Beginner human — high, tutorials from 2021–22 still rank well in search. Tool scaffold — n/a.
**Verdict: FAILS the stated bar as written** — one non-independent source, no measurement, and a false-positive population (legacy code) that is enormous and entirely legitimate. **Do not ship as a standalone tell.** It could be salvaged only as a *conditional*: deprecated-API density inside files whose git history is younger than the deprecation date. That conditioning is what makes it a tell, and this sweep found no source that has done it. Recommend keeping the regex in the codebase marked disabled-by-default with the conditioning requirement documented.

### MOB4 — Hardcoded font sizes instead of Dynamic Type
**Description:** `.font(.system(size: 17))` and scattered `.fontWeight(.medium)`/`.fontWeight(.semibold)` in place of `.font(.body)`/`.font(.headline)` and `bold()`.
**Support:** M23 only (one source, one author, no measurement).
**Regex:** yes — `\.font\(\.system\(size:\s*\d+` and `\.fontWeight\(\.(medium|semibold)\)`.
**Era:** all SwiftUI.
**False positives:** Expert human — moderate; deliberate typographic control is a legitimate choice and plenty of shipped Apple-featured apps do it. Beginner human — **extremely high**; designers-turned-developers reach for pixel sizes reflexively. Tool scaffold — n/a.
**Verdict: FAILS.** This is an accessibility defect (already owned by sweep 06), not an authorship signal. It cannot distinguish AI from a human who thinks in points. Reject as a tell; keep as an accessibility finding.

### MOB5 — Icon-only buttons with no accessibility label
**Description:** `Button { } label: { Image(systemName: "plus") }` with no text label, invisible to VoiceOver.
**Support:** M21 (named as an LLM failure mode) and M23.  Same author — **one source.**
**Regex:** partially; the multi-line `Button`/`Image(systemName:)` shape is not reliably matchable with a single regex and needs AST or a heuristic proximity match.
**Era:** all SwiftUI.
**False positives:** Expert human — moderate. Beginner human — very high; this is the most common iOS accessibility defect there is, with a decade of human precedent.
**Verdict: FAILS as an AI tell.** Real defect, wrong sweep — belongs in 06-accessibility. Listing it here would flag thousands of human apps.

### MOB6 — View body decomposed into `private var x: some View` computed properties
**Description:** A single large Swift file whose `body` is assembled from several `private var header: some View` / `private var content: some View` computed properties rather than extracted `View` structs; often alongside multiple type definitions in one file.
**Support:** M24 only. The author repeats the rule twice for emphasis, which suggests frequency in agent output, but that is inference from emphasis, not measurement.
**Regex:** yes — `private\s+var\s+\w+\s*:\s*some\s+View`.
**Era:** all SwiftUI.
**False positives:** Expert human — **high, and this is decisive.** Computed-property decomposition is actively taught in widely-followed human SwiftUI tutorials and is a defensible style; M24 itself concedes small helper properties "can be left alone". The rule is a performance preference (`@Observable` invalidation granularity), not a correctness rule.
**Verdict: FAILS.** A pattern that reputable human developers deliberately choose cannot be a tell. Reject.

### MOB7 — Glassmorphic bottom sheets and translucent floating tab bars
**Description:** Frosted/translucent blurred bottom sheet, floating pill-shaped translucent tab bar detached from the screen edge.
**Support:** none that survives scrutiny.
**Regex:** n/a — **rejected before the regex question matters.**
**Era:** n/a.
**Verdict: REJECTED, and this is a correction to the pre-2025 folk wisdom.** M33 establishes that since iOS 26 shipped (announced 2025-06-09), translucent refractive materials are the **Apple system material across every Apple platform**, present in the Dock, notifications and Control Center, explicitly "available to third-party apps", and that on-screen toolbars are no longer pinned to the bezels but separated into context-sensitive bubbles. Flagging translucency or a detached floating tab bar would therefore penalise platform-conformant design and would fire on Apple's own apps. (M33 does not state that a stock `TabView` receives the material automatically with zero code — that specific mechanism is unverified here; the rejection rests on the material being the documented system default and available to third parties, which is sufficient.) Note the tension with `05-mobile-and-copy.md` tell #8 (glassmorphism): that tell may still hold for *web* and for *pre-iOS-26 Android/Flutter* output, but on iOS 26+ it is invalid and must be scoped or suppressed.

### MOB8 — Tab-bar count (the "5-tab bottom bar" tell)
**Description:** A bottom tab bar with 4–5 items, icon-above-label.
**Support:** none. Contradicted by M32 and M26.
**Verdict: REJECTED — decisively, and this closes the open question 05 flagged.** M32 has the Android platform documentation instructing developers to use the navigation bar for "Three to five destinations of equal importance", with icon and label. Every well-regarded human iOS and Android app in existence — Apple's own, Google's own — sits in that range because the platform says to. Separately, M26 shows the official Expo scaffold ships **two** tabs, so a 5-tab bar is not even a scaffold default that could leak through. **A tell that fires on Apple Music, Instagram and the Play Store is not a tell.** Never flag tab count. If this appears in any existing skill rule, remove it.

### MOB9 — Oversized rounded corners on mobile cards
**Description:** Corner radii far above platform norms (e.g. 24–32pt on list cards).
**Support:** **none.** M27 — the only quantitative study located — measured web pages only and did not measure corner radius on mobile at all. M28's 16 patterns contain no radius item. No opened source measured mobile corner radii against a human-app baseline.
**Verdict: FAILS for lack of evidence, not because it is necessarily false.** The intuition may well be right, but there is no threshold anyone can defend. Note also that neither official scaffold examined here defines a border-radius token at all (M36 has none; M29 says FlutterFlow exposes radius as a theme setting but publishes no default), so there is not even a scaffold baseline to measure deviation from. Do not ship a radius threshold for mobile until someone measures a corpus. See Gap G1.

### MOB10 — AI-chat-wrapper store-listing and screenshot cluster
**Description:** Store screenshots showing a purple-to-blue gradient hero, a centered "type a question" prompt input with three example-question chips beneath it, a paywall card, and a bottom tab bar — combined with listing metadata containing "Your personal AI", "powered by GPT", "ask anything", "the smartest AI on iOS".
**Support:** M30 (substantive but vendor-interested, no measurement, no Apple citation) and M31 (confirms 4.3(b) tightened, but Apple's published text describes **category duplication**, not this visual cluster). So: **one substantive source, partly undercut by the second.**
**Regex:** yes, for the metadata half only — screenshots are not regex-addressable.
```
(?i)\b(your personal ai|powered by (gpt|chatgpt)|ask (me )?anything|smartest ai on (ios|iphone))\b
```
**Era:** 2023→present; likely to churn fast as phrasing shifts. `[STALE-RISK]`
**False positives:** Expert human — low for the metadata strings, but note that a *human* team shipping a legitimate ChatGPT-backed product writes these same words honestly. Beginner human — high. Tool scaffold — n/a. Critically, the visual cluster identifies a **product category clone**, not AI authorship: a human developer copying a top-grossing AI app by hand produces the identical screenshots.
**Verdict: FAILS the stated bar** (one interested source, no measurement) **but the metadata regex is cheap, low-risk and worth keeping as a copy-level flag**, scoped as "generic AI-product marketing language" rather than "AI-generated design". Do not claim App Review acts on it — no Apple source says so.

## Counter-evidence

**CE1 — The best quantitative AI-design measurement in existence explicitly excludes mobile.** M27 analysed 1,590 sites with Playwright and reports a clean distribution (22% high / 32% medium / 46% low). It is web-only and says so. Any mobile tell claiming this study's authority is misappropriating it. There is no mobile equivalent.

**CE2 — The widely-shared "16 patterns that out your app as vibe-coded" list contains zero mobile patterns.** M28's title says "your app"; all 16 items are web DOM/CSS constructs (colored left borders, badge-above-H1, stat banner rows). It is also a two-day-later restatement of M27, not independent confirmation. The apparent volume of "AI mobile tells" discourse is largely one web study being re-titled.

**CE3 — Glassmorphism inverted between 2024 and 2026 on iOS.** M33: Liquid Glass shipped system-wide in iOS 26 and third-party apps get it from stock components. What was plausibly an AI-slop tell in 2023 is now the strongest evidence that a developer used the platform correctly. Any glassmorphism rule inherited from earlier research must be date- and platform-scoped or it will invert its own meaning.

**CE4 — Apple's 2026 crackdown is about category duplication, not AI.** M31 quotes the new 4.3(b) text ("indistinguishable from what's already widely available") and Apple's named target categories are dating, flashlight, wallpaper, timer, fortune-telling, fart and drinking-game apps — a list that mostly predates generative AI. M30's claim that reviewers act on a specific AI visual signature is a vendor's inference, not Apple policy. The skill should not tell users that a given visual style risks rejection.

**CE5 — "v0 mobile output" is not a thing.** M34: v0 emits React/Next.js/Tailwind/shadcn web code and "does not generate React Native, Swift, Kotlin, or Flutter." The brief's premise here is mistaken. Any v0 contribution to a phone screen is web markup in a wrapper, so the web sweeps' tells apply and no native-mobile signature exists to look for.

**CE7 — The official React Native scaffold is monochrome, so "AI apps start colourful" is wrong for RN.** M36: the current bare `create-expo-app` default defines *no* accent or tint colour at all — text, background, and three neutral greys, with platform system fonts and a 4pt spacing scale. Two tabs, `Home` and `Explore`, rendered with the platform's own native tab bar. Where the older tabs template at least gave a blue tint (M26, `#2f95dc`), the current default gives nothing. Any gradient, purple, or custom-drawn tab bar in an Expo project was introduced deliberately — which strengthens the *inverse* argument (colour choices in RN are always authored, so they are legitimately attributable) while removing "the scaffold made it do that" as an excuse or an explanation.

**CE6 — Android's purple is Google's, not the model's.** M25: the Android Studio Empty Activity scaffold ships a purple/pink Material 3 palette *before any model is involved*. A meaningful share of the "AI always makes purple apps" impression on Android is the platform template leaking through unedited. This weakens, though does not eliminate, the purple-gradient tell in `05` when applied to Android.

## Gaps

**G1 — No mobile equivalent of the Krebs measurement exists.** I searched for any corpus study of mobile screens comparing AI-generated to human-made apps on measurable properties (corner radius, tab count, tab bar geometry, sheet styling, palette). Nothing found. This is the single biggest gap: **every mobile visual claim in this sweep and in `05` rests on practitioner observation.** Until someone measures screenshots at scale, mobile visual tells cannot be scored with confidence and the skill should say so in its own output.

**G2 — FlutterFlow's actual default values are unpublished.** M29 confirms 16 predefined default colors ship with every project but publishes no hex values, no default font family and no default border radius. Without them a "default FlutterFlow look" detector cannot be written. `05`'s note that flutterflowclub.substack.com is unfetchable still stands — I did not retry it. Closing this would need either the FlutterFlow editor itself or an exported project's `flutter_flow_theme.dart`.

**G3 — Figma Make has no visual critique in the literature.** The most on-topic 2026 comparison of AI mobile design generators (M35) covers Figma Make but is a feature matrix with no visual evaluation whatsoever. I found no source that examines Figma Make's mobile output characteristics. This is a genuine absence in the published record, not a search failure.

**G4 — No Jetpack Compose analogue of the SwiftUI agent-skill rule list.** The SwiftUI ecosystem has a named practitioner (Paul Hudson) cataloguing LLM-specific mistakes. I found no equivalent for Compose. Consequently Compose code-level evidence here rests entirely on scaffold defaults (M25), with nothing on Material2-vs-Material3 import staleness, deprecated Compose APIs, or Compose-specific LLM habits. Worth a targeted follow-up.

**G5 — Generic iconography is entirely unevidenced for mobile.** The brief asked about it. No opened source discusses SF Symbols / Material Icons / Lucide overuse or icon-set homogeneity in mobile AI output. M26 gives one concrete instance (the Expo scaffold reusing one icon across both tabs) but that is a template artifact, not a model habit. No candidate tell could be formed.

**G6 — Fetch failures (4 sources; none cited anywhere above).**
- `hackingwithswift.com/articles/281` ("What to fix in AI-generated Swift code") — HTTP 403 to WebFetch. This is the article framing the SwiftUI rule-set as LLM-specific; I recovered the framing from the repo README instead and cite that (M21). Article 282 on the same site was not attempted, since 281's 403 made it pointless. Neither article is cited.
- `nurxmedov.medium.com` (Mobbin / "every designer ships the same UI") — HTTP 403. This was the one candidate source that might have had a screen-corpus measurement behind it. Unknown whether it does.
- `developer.apple.com/design/human-interface-guidelines/tab-bars` — returns a title with no body (client-side rendered). **I therefore have no Apple-side source for iPhone tab-count guidance** and rely on the Android documentation (M32) for MOB8's rejection. An Apple-side confirmation would strengthen it.
- `m3.material.io/components/navigation-bar/guidelines` — same client-side rendering problem; substituted developer.android.com (M32).

*Two further pages fetched successfully but yielded nothing usable, and are not failures:* `vtsen.hashnode.dev`'s Compose template article did not contain the default hex values (obtained from the artifact instead, M25), and the FlutterFlow docs contained no default values (recorded as M29 / G2).

**G7 — Sample size on MOB1.** The Compose default palette was verified across two unrelated repositories plus a third showing the customized variant. Two is enough to establish the literal values are fixed, but it is not a frequency measurement — I have no figure for what share of shipped Compose apps still carry them, and therefore no base rate for the false-positive estimate.
